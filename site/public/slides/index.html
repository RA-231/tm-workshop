0.3 — The ESA dataset

The telemetry signal

It's anonymised and quantised — values are normalised, names are channel_41, units are stripped.

Most channels are staircases: they sit on a level, then step to another level.

So raw-value thresholds are weak. The information is in phase (which level, in what order) and duration (how long it dwells).

This drawing illustrates the labelled March-2000 anomaly on channel_41. We'll investigate it in Step 5.

The value 0.64 is inside the channel's normal range, so a range threshold would not identify it. Explain that the unusual feature is the long dwell at that level.
Step 1

On the way: what a table format is, and why the catalog matters.

1.1 — Iceberg table layout

How Iceberg tracks files and metadata

s3://warehouse/esa_adb/readings/
├── metadata/
│   ├── v3.metadata.json      ← schema, partitions,
│   │                            snapshot list
│   ├── snap-8231….avro       ← manifest list
│   └── 92f1…-m0.avro         ← manifests: which
│                                files + their stats
└── data/
    └── ts_month=2000-03/
        └── 00000-0-….parquet ← the rows

Reading

Find the current metadata.json → a snapshot → manifests → read only the files that survive your filters.

Writing

Write new Parquet → write new metadata that includes it → atomically swap the "current metadata" pointer.

Readers never see a half-finished write. That pointer swap is the commit.

Explain how an engine follows table metadata to find data files, and how an atomic metadata update commits a new table state.
1.1 — Iceberg table layout

Snapshots and coordinated commits

1 · Snapshots retain history

Retained snapshots describe earlier versions of the table, supporting time travel and rollback.

2 · The catalog manages commits

An atomic swap needs one coordinator every writer and reader agrees on. Object storage alone can't do it.

That coordinator is the catalog.

Next, we'll use Polaris to manage the catalog.

1.2 — The Polaris catalog

Apache Polaris

An implementation of the Iceberg REST catalog protocol. It tracks metadata locations and coordinates commits:

esa_adb.readings  →  "current metadata is v3.metadata.json"
                  →  atomic metadata update on commit

Flink and Trino use the REST protocol to access the same Polaris catalog. Both engines use the table metadata it provides.

They do not need to communicate directly; Polaris coordinates access to the table.

What we skipped

In production Polaris also does access control and vends scoped, temporary storage credentials per engine.

For the workshop, every engine uses the same static key for the local Garage object store.

If asked about catalog alternatives, explain that we chose Polaris because both engines support the Iceberg REST catalog protocol.
1.3 — Flink ingestion

Why Flink for a batch load?

Our job processes a finite set of files in streaming mode: the sink commits a new snapshot at every checkpoint, so the table grows in visible increments while the job runs.

The file source is bounded — once every file is read, the job ends by itself.

A live source could run continuously. This file source finishes when all input has been read.

One prep step first

ESA channels ship as pickled pandas DataFrames. Flink can't read those, so task data:prepare converts each to newline-delimited JSON under data/prepared/.

Same step converts the dataset's metadata into three dimension tables:

  • channels — what each one measures
  • labels — the anomaly windows
  • anomaly_types — the taxonomy

Step 2's views and Step 5's investigation use these metadata tables.

2.1 — Query with Trino

Querying with Trino

A distributed SQL engine that owns no storage. You give it catalogs (connector + config) and it federates queries across them.

Our iceberg catalog points at the same Polaris that Flink writes to. Trino asks "where's the current metadata for esa_adb.readings?", gets a pointer, and plans from there.

Polaris is the handoff point between the writer and every reader.

task trino    # interactive CLI
SHOW CATALOGS;
SHOW SCHEMAS FROM iceberg;

SELECT count(*) FROM iceberg.esa_adb.readings;

SELECT channel, count(*) AS samples,
       avg(value) AS mean
FROM iceberg.esa_adb.readings
GROUP BY channel
ORDER BY samples DESC LIMIT 10;
2.2.1 — Compare query filters

How the planner uses Iceberg metadata

EXPLAIN
SELECT avg(value) FROM iceberg.esa_adb.readings
WHERE ts_month = '2000-03';

Read the estimated rows on the table scan. Now widen the filter — BETWEEN '2000-03' AND '2000-09' — and explain again.

The scan tracks the filter because Trino reads Iceberg's metadata and prunes partitions and skips files before touching a byte of Parquet.

Compare query performance

  • Drop EXPLAIN, compare wall-clock
  • Trino UI → localhost:8080/ui/ → the query detail shows splits and bytes read
  • Filter on ts instead: column stats still skip files — but ts_month prunes whole partitions outright

Partition values and column statistics help Trino exclude files before reading them.

Run the narrow and wide queries back to back. Compare the bytes read in the Trino UI and relate the difference to the filters.
2.2.2 — Metadata and snapshots

Tables about the table

SELECT * FROM iceberg.esa_adb."readings$snapshots";

SELECT file_path, record_count, file_size_in_bytes
FROM iceberg.esa_adb."readings$files" LIMIT 10;

SELECT count(*) FROM iceberg.esa_adb.readings
FOR VERSION AS OF <snapshot_id>;

Every Flink checkpoint you watched in Step 1 is a row in that snapshots table. Pick an early one and count rows — you're reading the table as it was mid-ingest.

Time travel uses retained snapshots and the data files they reference.

2.3 — Telemetry views

Views for telemetry and anomaly labels

readings is the fact table: channel, ts, ts_month, value, plus five provenance columns (source_file, run_id, …) recording where each row came from. Step 1 also loaded channels, labels and anomaly_types. Define their joins as reusable views:

task trino:views

readings_enriched

readings ⋈ channel metadata — subsystem, physical unit, group.

anomalies

the labelled windows + their type, with ISO-8601 strings parsed into real timestamps.

labeled_readings

Every reading tagged with whether it falls inside a labelled anomaly.

labeled_readings is a range join — each reading matched to any window covering its timestamp. Superset uses it to colour anomaly periods, and the agent uses it to validate findings in Step 5.

3.2 — Gateway controls in LiteLLM

Why use LiteLLM?

LibreChat can connect directly to an OpenAI-compatible provider. LiteLLM adds gateway controls:

1 · Credentials

LiteLLM holds the provider key. Clients use a gateway key. Isolation is limited on a single-user laptop.

2 · Usage controls

Apply per-key budgets, rate limits, and spend tracking to requests routed through the gateway.

3 · Provider configuration

Map workshop-default to a provider and model without editing each client.

These controls require another service to run and maintain. A direct connection may be sufficient for personal use.

4.1 — Tool operations and restrictions

What the tools allow

An MCP server lets the model request data during an investigation.

The model decides

It selects tools to list tables, inspect schemas, and run queries.

It can use the results to revise a query or choose another tool.

You decide what's possible

Our server permits read-only queries and caps result sizes.

The query check rejects statements such as DROP TABLE.

The server defines which operations tools permit and enforces their limits.

5.2 — Start the three MCP servers

Host checks and the SSRF allowlist

1 · DNS-rebinding Host check

MCP's streamable-http transport only accepts localhost in the Host header, and returns 421 Misdirected Request otherwise.

Our servers reach each other by compose hostname, so: host_origin_protection=False for this local workshop stack.

2 · LibreChat SSRF allowlist

v0.8.7 blocks MCP URLs that resolve to private IPs unless the domain is allow-listed.

mcpSettings:
  allowedDomains:
    [mcp-server, trino-mcp, superset-mcp]

These settings allow connections using the workshop's Compose hostnames.

5.4.4 — Investigation instructions

Investigation instructions

You are a satellite-telemetry anomaly analyst. You have three MCP tool groups: trino (generic SQL
exploration), esa-adb (telemetry navigation + scored anomaly detectors), and superset (create
charts). Read the about://dataset resource first if your client exposes it.

The data is anonymized, quantized "staircase" telemetry — raw-value thresholds are weak; reason
about PHASE (which level, in what order) and DURATION (dwell).

Method:
1. Orient:      list_channels / channel_summary; note the time span.
2. Detect:      run phase_anomaly, plateau, data_gaps, stl_residual, cadence over a broad window.
                Scores are relative — they mean nothing in isolation.
3. Calibrate:   score a quiet window from the same channel and compare.
4. Zoom:        readings_around the worst segment; describe the observed signal changes.
5. Corroborate: cross_correlation against sibling channels in the same group.
6. Visualize:   anomaly_overlay_chart(channel), then add_to_dashboard; return the URL.
7. Validate: do not call anomalies_for during detection. After recording your findings,
                compare them with the labels (hits, misses, false alarms).

Report a ranked list: channel, window, the scores that flagged it vs the nominal comparison, a
phase+duration explanation, the chart URL, and your confidence.
Highlight the description of staircase signals and the calibration step. Explain that labels are reserved for validation so the investigation must produce findings from the signal first.
5.5 — Anomaly detector scores

Six detectors returning numeric scores

ToolWhat it scores
phase_anomalyunusual levels, dwell durations, and transitions
plateauabnormally long "stuck" flat runs
data_gapsdropouts — worst gap vs the dominant sample interval
stl_residualdepartures from the channel's own trend and season
cadencesampling jitter and drift (regularity, not dropouts)
cross_correlationdecorrelation from sibling channels (multivariate)

The agent compares scores from suspect and nominal windows to decide which findings to report.

5.9 — Troubleshoot LibreChat

LibreChat limitations (v0.8.7)

  • Resources/prompts missing? Expected — LibreChat doesn't surface them. Use Claude Desktop or Claude Code to see them.
  • Malformed tool calls? Tool-calling must be validated per model. Try dropParams on the custom endpoint, or switch models. Use workshop-default for the workshop exercises.
  • Want to share your agent? Use Share — there's no create API in 0.8.7.
  • Tool list looks truncated? v0.8.7 paginates tools/list with an aggregate budget. 19 tools across three servers is comfortably inside it.
  • Max Agent Steps (recursionLimit) defaults to 25 — raise it if a long investigation gets cut off mid-trace.
